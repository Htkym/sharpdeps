## 実装内容

1. **宣言の索引**：namespace/type/memberを、所有するプロジェクト変種・包含関係・宣言位置つきで収集する。
   型は `partial` / `nested` / `file-local` / `generic(arity)` を識別し、kind（class/struct/interface/enum/delegate/record）と
   実効アクセシビリティ（file-localは `file`）を記録する。top-level statementsの有無も検出する。
2. **ID**：`Core.Identity` の規則をそのまま使う。宣言キーはdocumentation comment IDを優先し、
   無ければ名前空間+包含型チェーン+arity の構造型キーにフォールバックする。
   parameter型の表示は完全修飾かつ特殊型を使わない形式（`System.Int32`）に固定し、
   キーと表示が食い違わないようにした。
3. **Compilation横断の解決**：`SymbolResolver` が「所有変種→アセンブリ名→定義変種」のマップで
   参照先の定義変種を決める。マップは `SemanticReferenceMap` が解決済みProjectReference
   （直接＋推移）から作り、**マルチTFMでも取り違えない**（`Domain(net10.0)` と
   `Domain(netstandard2.0)` は別のアセンブリ解決先になる）。
   解決できないシンボル（型パラメータ・error型・匿名型）は `null` を返し、確定した型へ昇格させない。
4. **外部型**：解決マップに無い型は `AssemblyIdentity` と宣言キーで識別する。NuGetパッケージ名は推定しない。
   配列・ポインタは要素型へ、構築ジェネリックは定義へ正規化し、型引数は別途採取する前提にした。
5. **位置索引**：文書ID + オフセットから、その位置を含む最も内側の型を返す。
   同じファイルが複数変種に属する場合は**変種ごとの候補**を返し、どれか一つを勝手に選ばない
   （SD-019で有効プロファイルに応じて選択する）。
6. **文書レジストリ**：`Identity.DocumentId(rootId, 相対パス, origin)` を使い、
   Quick解析と同じ規則で文書IDを作る。同じファイルはどちらの解析でも同じIDになる。

## 未検証事項

- 索引からv2 `AnalysisSnapshot.types[]` への出力は未実装（SD-012/013で集計と合わせて実装）。
  そのためSemanticHostの出力に型一覧はまだ含まれない。
- メンバーの `publicSurface` 判定はSD-009で実装する（本タスクではアクセシビリティのみ記録）。
- 位置索引の変種選択（有効プロファイルの決定）はSD-019で実装する。
- 参照循環を含む推移解決の実測（ロジックはSD-007の制限つき）。
- `SymbolResolver` の外部メンバーIDは `AssemblyIdentity` を変種キーの代わりに使う規約で、
  TS実装との golden 値固定は型IDのみ（メンバーIDは未固定）。

## 判断・補足

- 索引はプロジェクト変種ごとに型を複製して持つ（同一型でも変種が違えば別ノード）。
  これは「異なるTFMの辺をunionしない」というSD-002/006の方針と揃えている。
- `TryGetTargetFramework` などローダーの内部計算を `VariantKeyFor` に集約し、
  索引・参照マップ・プロファイルが同じ変種キーを使うようにした。
- テスト用のインメモリ索引は `TRUSTED_PLATFORM_ASSEMBLIES` を参照に使い、
  MSBuildに依存せず宣言・フラグ・位置索引の挙動を固定できるようにした。

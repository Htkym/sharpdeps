## 実装内容

1. Quick（file-based app、SDK不要）とSemantic（csproj、MSBuild/Roslyn）をプロセスレベルで分離した。
   SemanticHostは終了コード `0`/`2`/`1` で「成功（部分含む）」「前提条件不足」「想定外エラー」を区別する。
2. MSBuildLocatorの登録を `NoInlining` の独立メソッドへ分離し、ローダーは未登録を拒否する。
   `MSBL001` に従い `Microsoft.Build.Framework` を `ExcludeAssets="runtime"` で参照し、
   配布物へMSBuild本体を含めないことをpublish出力で確認した。
3. `OpenSolutionAsync`（.sln/.slnx）と `OpenProjectAsync`（単一プロジェクト）の両経路を実装した。
4. Roslynの `Project` にTFMが無いことを実測で確認し、プリプロセッサシンボルから導出する方式にした。
   取得できない場合は未解決として記録する（名前による結合をしない）。
5. `ProjectReference` を変種単位で解決する純粋ロジック（`ProjectVariantResolver`）を実装し、
   完全一致・互換・曖昧・非互換・候補なしをテストで固定した。
6. 評価済みCompile items、条件付き参照、linked file、Compile Remove、global.json、未restore、
   コンパイルエラー件数を試作レポートへ記録するようにした。
7. fixtureを2種類用意し、正常系は無エラー、失敗系は診断つきで例外を出さないことを検証した。

## 未検証事項

- SDKが無い環境でのSemantic初期化失敗（`DOTNET_ROOT` を空にしてもSDK探索が成功したため再現できず）。
- 旧式.NET Framework（非SDKスタイル）プロジェクト、VB/F#/C++の意味解析、Linux/macOS。
- 非C#プロジェクトを含むソリューションのロード（実装はあるがfixtureで未使用）。
- 推移的ProjectReferenceがワークスペースに現れない問題への対処（SD-007で決定）。
- ロードが `obj/` へ書き込む副作用の範囲（実測では `AssemblyInfo.cs` 等。ユーザーソースは不変）。

## 判断・補足

- 解析器ソリューションは `.slnx`（.NET 10 SDKの既定）とした。SDK 10.0.300で
  `dotnet build` / `dotnet test` / `dotnet sln` が動作することを実測した。
- RoslynはQuick 4.14.0 / Semantic 5.9.0 と系列が異なる。プロセス分離により共存し、
  実測で競合していない。理由と影響はADR 0001に記載した。
- `analyzer/Directory.Build.props` がfile-based appへ波及しないよう、`build-analyzer.js` に
  `-p:ImportDirectoryBuildProps=false` を追加した（SD-005でQuickHostへ移行するまで維持）。
- VSIXには `analyzer/src/**`・`analyzer/tests/**`・`analyzer/bin/semantic/**` を含めない
  （SemanticHostはまだ拡張機能から使わないため）。同梱方針の最終判断はSD-029で行う。
  Quickの配布物（`analyzer/bin/code-map.dll` 一式）は従来どおり含む。

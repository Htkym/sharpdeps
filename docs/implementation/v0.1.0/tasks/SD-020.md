## 実装内容

1. **SCC一覧と実在閉路の分離**：射影に`cycleGroups`（`memberIds`の集合・内部辺・witness）を同梱し、
   Cyclesタブでは「メンバー（名前順の集合。**経路ではない**と明記）」と「実在する閉路（witness、
   順序が経路）」を別ブロックで表示する。witnessがないグループは「閉路未確認」と明示する。
2. **辺→根拠**：witnessの各辺はボタンで、クリックすると`relationSelected`が発行されInspectorの
   根拠一覧（SD-018）へつながる。グループの「この循環を表示」で`scope: {kind:'cycle'}`の射影を要求する。
3. **表示上限外の取り込み**：射影の表示予算は**スコープ起点を最優先**で残すようにした。
   循環スコープのメンバーと、エディターからのreveal対象（SD-019）が上限で消えない。
4. **被依存候補**：Inspectorは直接の依存/被依存（根拠付きの事実）と出/入の箇所数を示す。
   推移的な「影響の可能性」は深さ付きスコープ（dependencies/dependents、深さ1〜3）で表示し、
   事実（根拠）と区別する。深さの数値表示はSD-021以降の課題として残す（下記）。
5. **Problems連携**：`CycleDiagnostics`は解析IDを保持し、実行開始時に必ずクリアする
   （別analysisIdの状態が混ざらない）。Quickは「（Quick解析: 推定診断）」を付けて推定であることを
   示し、Semanticはwitnessの各辺の**実在する根拠位置**へ診断を置く。根拠が生成文書にある場合は
   リポジトリ外を指さないようProblemsには出さず、witnessがないグループは出力チャネルに記録する。

## 未検証事項

- **深さ付き被依存の数値表示**：推移的な被依存はスコープ（深さ1〜3）で表示できるが、各ノードの
  ホップ数を数値で示す実装は未着手（必要なら次の段で射影ノードに`depth`を追加する）。
- **Problemsの実機確認**：Semanticの循環診断が実際のProblemsパネルで正しい位置に出ることは
  VS Code実機での確認が必要（SD-027）。ロジックは実解析出力とユニットで確認した。
- **循環スコープの実データ表示**：ブラウザfixtureは合成データ。実プロジェクトの循環での見え方は
  SD-027で確認する。
- グループが非常に多い場合の一覧仮想化は未対応（現状は全件表示）。

## 判断・補足

- 循環の「集合」と「経路」を別データとして扱い、UIでも別ブロックにした。ソート済みメンバー一覧を
  経路として読めてしまう誤解を避けるため。
- `cycleGroups`は射影メッセージに同梱した。件数が少なく、ビューは一覧とwitnessを同時に必要とする
  ため、往復を増やすより同梱が素直だと判断した（プロトコルのスキーマにも明記）。
- 表示予算の優先順位は「スコープ起点 → 次数」。起点が消えると、revealや循環スコープが
  「何も見えない」状態になるため。

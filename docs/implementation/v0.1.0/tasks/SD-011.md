## 実装内容

1. **生成document取得と区分**：ロード時に`GetSourceGeneratedDocumentsAsync`で各変種の
   生成文書を取得し、`GeneratedSourceDocumentInfo`（変種・プロジェクト・ハンドル名・
   ワークスペースパス・SHA-256・サイズ・内容）としてロード結果へ載せる。
   文書レジストリは**仮想相対パス** `generated/{project}/{hint}` と`origin: generatedSource`
   で登録し、コンパイル中の構文木はワークスペースパスで一致する。これにより生成コード内の
   根拠は`generatedSource`・生成文書ID・生成ハッシュを持つ（objパスはレポートへ出ない）。
2. **内容/hashの保持**：内容は解析結果と同じディレクトリの`generated/{documentId}.cs`へ
   UTF-8（BOMなし）で書き出す。1文書1MiBを超える場合は内容を保持せずハッシュのみとし、
   `semantic.generatedDocumentTooLarge`で明示する。利用者リポジトリへは何も書かない。
3. **物理位置とmapped locationの分離**：`physicalSpan`と`mappedLocation`を別フィールドで
   出力する（前回分、契約テストで検証済み）。
4. **read-only provider**：`sharpdeps-generated:/{analysisId}/{documentId}`を
   `TextDocumentContentProvider`で解決する。URIは不透明IDのみで、内容は登録済み解析結果から
   読む。保持されていない文書は開かずエラーにする（ディスク上の古いファイルへは落ちない）。
5. **capabilities/completeness**：生成文書が1件以上あれば`generatedDocuments: true`。
   取得失敗（`semantic.generatedDocumentsUnavailable`）・内容取得失敗
   （`semantic.generatedDocumentContentUnavailable`）がある場合、`completeness`は
   `completeWithinScope`にならない。
6. **read-only仮想URIの安全性**：`reportStore.readGeneratedDocument`は
   `origin === 'generatedSource'`かつ`doc_`+16桁hexのIDのみを受け、`safeJoin`で
   レポートディレクトリ内の`generated/`に限定する。上限4MiB。

## 未検証事項

- **大規模生成物**：Razor等の大量・巨大な生成文書でのメモリと所要時間は未計測（SD-029の性能計測）。
- **SDKなし環境**：`GetSourceGeneratedDocumentsAsync`が失敗する環境での`completeness`表示は

- **UIでの表示**：providerの登録のみで、根拠から生成文書を開く導線（SD-019）は未実装。
  VS Code実機でのprovider表示はSD-028のE2Eで確認する。
- ジェネレーターが`IIncrementalGenerator`以外（旧`ISourceGenerator`）の場合の取得は未確認。
- 型そのものに「生成由来」フラグは付けない（根拠の`generatedEvidenceCount`と文書originで判別する）。

## 判断・補足

- 生成文書のIDは仮想パスから作る。objの実パスをID・manifestへ出すと、機械固有のパスが
  レポートへ混入し、同じコードでも結果が環境依存になるため。
- 内容はレポートディレクトリ配下に置き、URIはIDのみとした。manifestに内容ファイルのパスを
  持たせると、レポートが任意パスを指せる状態になる（信頼境界）。命名規則（
  `generated/{documentId}.cs`）をC#側とTS側で共有し、双方のテストで固定する。
- 保持は「解析結果と同じ寿命」であることを優先し、グローバルなキャッシュは作らない。

## 実装内容

1. v2モデル（`AnalysisSnapshot`）と根拠レコードをContractsへ実装し、
   `ambiguousCandidates`（同名候補が複数ある場合の候補数）を契約へ追加した。
2. ID生成をC#で実装し、TS実装と同一のgolden値を両言語のテストで固定した
   （`wrk_65aa6de15d22cae5` など）。片方だけ変えると両方のテストが落ちる。
3. 既存の解析パスへ索引収集を追加した。文書（相対パス・SHA-256・サイズ）、
   namespace宣言、using（位置つき）、global using、ProjectReference（行位置つき）を
   同じ1回の走査で記録する。**v1レポートの計算は変更していない**（回帰スナップショットで確認）。
4. マッパーはv1結果と索引からv2を構築する：
   - namespaceはプロジェクト変種ごとに分離（`ns_` = variant + 完全修飾名）
   - usingの参照先が同名で複数ある場合は全候補へ辺を張り、`ambiguousCandidates` と
     `quick.namespaceAmbiguousCandidates` 制約で明示する（一意決定をしない）
   - global usingは宣言位置を根拠として、プロジェクト内の各ファイルへ適用する
   - 循環は解析済みの全関係から計算し、表示上限の影響を受けない。witnessは持たない
   - 根拠は `relationId` 順のNDJSONとし、`evidenceIndex` に開始byte位置と件数を記録する
5. QuickHostは `report.json`（v1、既存の拡張機能用）に加えて `report-v2.json` と
   `evidence.ndjson` を出力する。Extensionを壊さずにv2を検証できる移行期間の構成。
6. 契約テストを実アナライザー出力に対して実行するよう追加した（SD-002の未達条件を解消）。

## 判断・補足

- 移行期間は v1 と v2 を同時出力する。v1経路は SD-013/SD-015 でUIがv2へ切り替わった時点で
  削除する（二重保守を続けない）。
- 索引収集は既存走査へ追加する方式にした。ファイルを2回読む実装を避け、
  大規模ソリューションでの解析時間を増やさないため。
- `ProfileHash` はTSと同じく16進16文字（prefixなし）。他IDは `prefix_` + 16文字。
- ProjectReferenceの根拠範囲は宣言行（属性の厳密範囲ではない）とし、制約
  `quick.xmlSpanIsDeclarationLine` で明示した。
- 生成された回帰スナップショットは `.prettierignore` で整形対象外にした
  （生成物であり、比較は値で行うため）。v1/v2とも更新手順は
  `SHARPDEPTS_UPDATE_BASELINE=1` のまま。

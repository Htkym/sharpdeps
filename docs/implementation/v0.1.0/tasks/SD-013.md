## 実装内容

1. **登録と検証**：`report-v2.json` をruntime validatorで検証し、`evidenceIndex.fileName` が
   **レポートディレクトリ内の単一ファイル名**であることを確認してから登録する。
   ファイルサイズ上限（レポート32MiB / 根拠512MiB）、根拠の件数と実ファイル行数の一致、
   行単位のJSONと根拠レコードの検証を行う。1つでも外れたら登録しない。
2. **ページング**：検索・根拠とも既定100件、上限500件。カーソルは `cur_` + ハッシュの
   不透明値で、ストア内の対応表が無い・別リクエストの・別クエリのカーソルは拒否する。
   Webviewからパス・byte offset・行番号を受け取る経路は無い。
3. **根拠の読み出し**：`evidenceIndex` の `startByte` から、**行単位**で読み出す。
   UTF-8はストリーミングデコーダで復号し、途中のマルチバイト文字から開始しない
   （索引が文字の途中を指す場合は安全にエラーになる）。
4. **世代管理**：登録済みが無ければ `unknownAnalysis`、別の解析が登録済みで
   要求IDが一致しなければ `staleAnalysis`。登録数上限を超えたら古い解析を破棄する。
5. **bridge**：protocol v2のメッセージを検証（未知type・不正IDは拒否）してから
   ストアを呼ぶ。ストアのエラーはコード付きの `error` 応答へ変換する。
   `analyze`/`cancelAnalysis`/`export`/`openX`/`persistViewState` は
   **`bridge.notImplemented` を明示的に返す**（黙って受け付けない）。実装はSD-014/019/021/022。
6. **射影**：`getProjection` はスコープ（root / 近傍depth 1〜3）・粒度・予算を受け、
   総数・省略数・`truncated` を必ず返す。フィルターの完全なモデルはSD-016で実装する。

## 受入条件の照合

| 受入条件 | 結果 |
|---|---|
| 大きなEvidenceでも初回renderに全件を含めない | 満たす。根拠はページ単位（既定100件）でしか返さず、実出力テストで `items.length < total` を確認 |
| 改竄cursor・境界外パス・欠損ファイルで安全なエラーになる | 満たす。それぞれ `invalidCursor`/`invalidEvidence`/`ioError` で拒否（テスト済み） |
| UTF-8日本語の途中から切れたページを生成しない | 満たす。行単位読み出し＋ストリーミング復号。日本語・絵文字のページ取得と、文字途中開始時の安全な失敗を確認 |

## 未検証事項（明示）

- **C#側のSemantic writerは未実装**。現状 v2 を出力するのはQuickHostのみで、
  結果ストアの統合テストもQuickの実出力を使っている。Semantic側の
  レポート書き出し（`Analysis.Core/Reports`）は、生成文書の取り扱い（SD-011）と
  合わせて実装する必要がある。**SD-013の「writer」成果物は部分的**である。
- パネル（`codeMapPanel`）と Webview はまだこのストアを使っていない。接続はSD-015。
- 検索索引は線形走査で、大規模データでの性能は未計測（SD-028）。
- 射影のフィルター（カテゴリ内OR/カテゴリ間AND）と文字列検索のインデックス化はSD-016。

## 判断・補足

- カーソルは「ストア内の対応表」方式にした。offsetを署名して埋め込む方式より
  改竄耐性が高く、失効も `release` で確実に行える。
- 根拠件数の不一致で登録を拒否するのは、途中書き込みのmanifestを読ませないため
  （計画書5.4の「原子性」要件）。
- bridgeが未実装機能を明示的にエラーにすることで、UIが「押しても何も起きない」状態に
  ならないようにした。

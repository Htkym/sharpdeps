## 実装内容

1. **推移的ProjectReferenceの解決**：MSBuildWorkspaceは直接参照しか公開しないため、
   参照の推移閉包を計算し、メモリ上のCompilationへ `AddReferences` で追加した。
   プロジェクトファイルもワークスペースも変更しない。追加件数は
   `AddedTransitiveReferences` と制約 `semantic.transitiveReferencesAdded` に記録する。
2. **書き込みの排除**：当初 `MSBuildWorkspace.TryApplyChanges` で推移参照を追加したところ、
   **フィクスチャの `.csproj` が実際に書き換わった**（`<ProjectReference>` と `<Name>` が追記）。
   ユーザーソースを変更するため設計を変更し、Compilationへの追加だけにした。
   ソースが変更されないことを統合テストで固定した。
3. **参照の循環**：推移閉包の解決中に循環を検出した場合は `semantic.projectReferenceCycle` として
   記録し、循環参照は追加しない（無限再帰を防ぐ）。
4. **プロファイル**：`Configuration`・`Platform`・プロジェクト別TFM・`profileHash` を結果に含める。
   `profileHash` は構成とTFM選択の組み合わせから作り、変更時は別解析として扱う。
5. **実用的な診断**：コンパイルエラーIDから利用者が対応できる分類へ変換する。
   - 解決失敗（CS0246/CS0234/CS1069/CS1705）→ `semantic.referencesUnresolved`
     （`dotnet restore` の実行を案内。自動restoreはしない）
   - 言語版（CS8630/CS8400/CS9058）→ `semantic.languageVersionUnsupported`
6. **失敗プロジェクトの可視化**：ワークスペース診断に現れたプロジェクトファイルを
   `LoadState: failed` として結果へ含める（黙って消さない）。
7. **Compilationの公開**：`SemanticLoadResult` が変種キー→Compilationを返し、
   SD-008/SD-010の収集器がそのまま使えるようにした（解析の二度手間を避ける）。

## 未検証事項

- 言語版非対応（CS8630等）の実再現（診断変換のロジックは実装済み、fixtureなし）。
- 非C#プロジェクトを含むソリューションのロード。
- SDKなし環境での初期化失敗経路（SD-029）。
- 参照循環を含むソリューションの実測（ロジックのみ）。
- Semanticのv2出力（`AnalysisSnapshot`）は未実装。SD-008以降の収集器と合わせて実装する。

## 判断・補足

- 推移参照は「宣言された参照」と「コンパイラが見る参照」の差である。v2モデルでは
  `projectDeclared` と `projectEvaluated` の区別で表す（SD-008/SD-012で写像）。
  今回の試作レポートでは制約として件数のみ記録する。
- `SemanticLoader` は `Analysis.Core` のみ参照する（`Analysis.Quick` は参照しない）。
  QuickはRoslyn 4.14.0、Semanticは5.9.0を使うため、プロセス内での系列混在を避ける。
- `TryApplyChanges` を使わない理由はADR 0001と対応表に明記した。

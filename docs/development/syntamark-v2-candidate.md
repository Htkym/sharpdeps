# Syntamark v2 consumer candidate

This is an opt-in development candidate, selected with
`SharpDepsUseMarkdownSessionCandidate=true`. Production remains pinned to
Syntamark 1.2.0. Neither this update nor successful candidate checks authorize a
SharpDeps release.

## Producer identity

- Source: [Syntamark PR #22](https://github.com/Htkym/syntamark/pull/22), commit
  `51b36faef56510cedccee288326874e31dbdefd2`.
- Producer: [successful CI 43662685388](https://github.com/Htkym/syntamark/actions/runs/43662685388).
- Private runtime/Source pair: `2.0.0-preview.89831114732901`.
- Contract: `2.0`; Markdown profile: `lithosharp-markdown/1`;
  YAML profile: `native-yaml/1`.
- Exact package, assembly and canonical-source hashes are retained in
  `docs/contracts/markdown-session-candidate-pin.json` and the producer's
  `eng/markdown/session-feed/pair-manifest.json` (producer fields preserved;
  repository formatting applied).

The previous candidate packages remain in the feed as historical evidence;
exact package references select only the new pair. The candidate consumes the
runtime package. Its Source package is restored and byte-verified, not compiled
into SharpDeps.

## Compatibility changes

Syntamark v2 includes native YAML and has no YamlDotNet package dependency. The
candidate removes SharpDeps' now-unnecessary direct YAML reference, verifies the
empty runtime dependency set, and binds loaded facts to contract 2.0 and the
native YAML profile. The stable path retains its original package, assembly,
dependency and contract checks.

Native YAML preserves invalid mappings, including duplicate keys, for source
inspection. SharpDeps must not turn those retained nodes into document titles,
metadata search fields or explicit symbol bindings. Metadata projection now
requires `MarkdownFrontMatterState.Parsed`; raw facts and diagnostics remain
available. Coverage includes direct analysis, prepared projection, cache reuse,
and valid-to-invalid-to-valid transitions.

The three accepted v1 conformance fixtures remain unchanged. A field-by-field
comparison of their stable and candidate normalized facts found only two
additions: `YamlProfileId` and the disabled `footnotes` capability for the pinned
profile. Candidate tests assert those additions separately, then compare every
original normalized fact against the existing hashes. They do not replace the
golden hashes with outputs generated by the new parser.

## New API applicability

- Native YAML is used automatically by the candidate. Typed metadata policy
  remains owned by SharpDeps; invalid syntax is not a typed mapping.
- Incremental sessions remain opt-in and retain their existing lineage,
  cancellation, fallback and transactional-cache checks.
- The new `syntamark-docs/2` profile, footnotes and directive attributes are not
  silently enabled. SharpDeps' graph contract still explicitly supports the
  pinned `lithosharp-markdown/1` profile. Supporting another profile would need a
  separate graph and coverage contract.
- Guarded link edits and composed source maps do not belong in this read-only
  indexing path. SharpDeps receives original source text and does not rewrite
  links, resolve site routes or render transformed pages.
- Selected-analysis APIs do not replace the current all-facts graph projection,
  which needs headings, sections, links, fences, text and metadata. No extra parse
  or speculative adapter is introduced.

## Formal release gate

On 2026-11-15, both the authoritative GitHub releases and NuGet version index
reported 1.2.0 as the latest formal release. The private v2 pair is not a formal
release, regardless of its successful CI.

Before changing production pins, verify the formal Syntamark runtime/Source pair
and its producer identity, replace both exact package identities and parser
stamps together, reassess API/feature differences since this candidate, and run
the resulting exact-head consumer and installed-package checks. SharpDeps release
must wait for that formal Syntamark release and completion of these checks.
